# `@bear-harness/i18n` module reference

## Responsibility and ownership

`packages/i18n` owns product/interface copy and the runtime that selects a product locale. It does not own the copy authored by a character package. The canonical Simplified Chinese catalog states this boundary in its module comment: character-package copy remains separate. The settings catalog makes the same contract visible to users: changing the interface language changes the application interface only, while a character package keeps its own language and may show a cross-language warning.

The module currently owns three product locales:

| Locale | Source of truth | Maintenance rule |
| --- | --- | --- |
| `zh-CN` | [`src/locales/zh-CN.ts`](../../packages/i18n/src/locales/zh-CN.ts) | Canonical catalog and key shape. Add product keys here first. |
| `en` | [`src/locales/en.ts`](../../packages/i18n/src/locales/en.ts) | Hand-maintained English copy with the same object shape as `zh-CN`. |
| `zh-TW` | [`src/locales/zh-TW.generated.ts`](../../packages/i18n/src/locales/zh-TW.generated.ts) | Generated from `zh-CN` with OpenCC; never edit this file directly. |

The catalogs are organized by product surface rather than by consuming component: `shell`, `composer`, `sidebar`, `threadHead`, `backstage`, `packageWorkshop`, `webDev`, `messages`, `memory`, `settings`, `modelSetup`, `language`, `errors`, `canonStudio`, and `work`. Product UI should use these keys instead of embedding equivalent interface copy in an application or package.

### Product copy versus role-package copy

A character package remains the source of truth for character-specific language, onboarding prose, answer choices, identity/canon text, roleplay labels, and package assets. The product catalog supplies the surrounding application chrome and fallbacks. In particular:

- The product language warning (`language.warningTitle`, `language.warningBody`) explains that package copy is not automatically translated.
- `canonStudio.packageManaged` labels package-provided canon as read-only; this is product UI copy, not a translation of the canon itself.
- The companion UI's work panel accepts package `work_presentation.labels` for role-specific titles and action/status labels, falling back to product keys when a label is absent. See [`WorkPanel.tsx`](../../packages/companion-ui/src/WorkPanel.tsx).
- The first-meeting UI renders the active package's validated onboarding definition and intentionally owns no step labels, prose, answer options, or transition rules. See [`FirstMeeting.tsx`](../../packages/companion-ui/src/FirstMeeting.tsx).

When changing a product button, heading, status, error, or accessibility label, add/change a key in this module. When changing what a character says or how its onboarding/roleplay is worded, change the character package contract and its package data instead. Do not copy package prose into `zh-CN` merely to make one role appear localized.

## Catalog shape and typed translation keys

[`src/locales/index.ts`](../../packages/i18n/src/locales/index.ts) imports all three catalogs and exposes:

- `supportedProductLocales = ["zh-CN", "zh-TW", "en"] as const`;
- `ProductLocale`, derived from that tuple;
- `resources`, mapping locale codes to their catalog objects;
- the individual `en`, `zhCN`, and generated `zhTW` exports.

Each catalog is declared `as const`, so literal key/value structure is retained. `src/index.ts` augments `i18next` with `CustomTypeOptions`: the default namespace is `shell`, the resource type is `typeof zhCN`, and both namespace and key separators are `.`. This gives i18next/Solid-i18next callers typed key completion and catches invalid key paths in typed call sites. The canonical key tree is therefore `zhCN`; the other catalogs must remain structurally compatible at runtime.

The catalog test is the localization gate for parity. [`tests/catalogs.spec.ts`](../../packages/i18n/tests/catalogs.spec.ts) verifies that:

1. the public `@bear-harness/i18n/locales` export resolves to the same `zh-CN` value as the internal resource;
2. `supportedProductLocales` is exactly `zh-CN`, `zh-TW`, `en`, and every locale has the same recursively computed object shape as `zh-CN`;
3. English contains no Han-script strings; and
4. representative Taiwan strings are the expected phrase-level OpenCC output.

There is no separate handwritten `zh-TW` catalog to keep in sync. A key added to `zh-CN` must also be added to `en`; the generated Taiwan catalog receives it through the generation step. Do not add a key only to English or only to the generated file. The parity test is runtime structural validation rather than a compile-time constraint on the `en` object.

### Interpolation contract

`i18n.init` configures `prefix: "{"` and `suffix: "}"`, so product placeholders are normally written as `{model}`, `{count}`, `{size}`, `{revision}`, `{roleLanguage}`, or `{userLanguage}`. Keep placeholder names and meaning stable across catalogs. `escapeValue` is explicitly `false`; translations and interpolated values must therefore be treated as already unescaped by i18next. Keep interpolated values constrained and render translation output as text, not as trusted HTML.

There is one confusing catalog inconsistency to resolve deliberately: `canonStudio.sourceLanguage` currently uses `{{language}}` while the other catalogs' interpolation examples use `{name}`-style placeholders. Check the rendered result before introducing another spelling; the configured delimiter contract should be the default for new copy.

## Runtime API, provider, and hooks

The package root export is [`src/index.ts`](../../packages/i18n/src/index.ts). Its public runtime surface is:

- `i18n`: one `i18next` instance initialized with all resources;
- `setProductLocale(locale: ProductLocale)`: persist and apply a locale;
- `ProductLocale` and `supportedProductLocales`: locale type and supported values;
- `I18nextProvider`: the Solid context provider re-exported from `solid-i18next`;
- `useLanguage`: the Solid-i18next language signal hook;
- `useTranslation`: the Solid-i18next translation hook.

The package manifest exposes the compiled root as `@bear-harness/i18n` (`dist/index.js` and `dist/index.d.ts`) and the locale registry as `@bear-harness/i18n/locales` (`dist/locales/index.js` and its declaration). `resources` is not re-exported from the root; use the locale subpath when direct catalog access is required (for example, tests or source-based accessibility assertions).

A Solid application should pass the shared instance to the provider and hooks, for example:

```tsx
import {
  I18nextProvider,
  i18n,
  useLanguage,
  useTranslation,
} from "@bear-harness/i18n";

function ProductShell() {
  const [t] = useTranslation(undefined, { i18n });
  const [locale] = useLanguage(() => i18n);
  return <h1 lang={locale()}>{t("shell.fallbackComposerPlaceholder")}</h1>;
}

export function App() {
  return (
    <I18nextProvider i18n={i18n}>
      <ProductShell />
    </I18nextProvider>
  );
}
```

Use `t("group.key")` for reactive component copy. For non-component helpers that already have access to the singleton, `i18n.t("group.key")` is the corresponding direct lookup. The default namespace is `shell`; other top-level catalog groups are addressed through their dotted key paths.

## Locale selection and lifecycle

The module performs selection during module evaluation:

```mermaid
flowchart TD
    A[Import @bear-harness/i18n] --> B[Read localStorage bear-harness.product-locale]
    B --> C{Value is supported?}
    C -- no --> D[Use zh-CN]
    C -- yes --> E[Use stored ProductLocale]
    D --> F[Set document.documentElement.lang]
    E --> F
    F --> G[Create i18next instance]
    G --> H[Initialize resources and fallback zh-CN]
    I[setProductLocale(locale)] --> J[Write localStorage]
    J --> K[Set document.documentElement.lang]
    K --> L[i18n.changeLanguage(locale)]
```

The persistence key is `bear-harness.product-locale`. A stored value is accepted only when it exactly matches a member of `supportedProductLocales`; any absent or unsupported value falls back to `zh-CN`. The document language attribute is set when a document exists, which keeps non-DOM contexts from requiring `document`. i18next is initialized synchronously (`initAsync: false`) with `fallbackLng: "zh-CN"`, `defaultNS: "shell"`, all top-level `zhCN` namespaces, dotted separators, and the interpolation settings above.

`setProductLocale` writes the selected locale to local storage, updates the document language attribute, and calls `i18n.changeLanguage`. Components using `useLanguage` or `useTranslation` observe the shared i18next instance and update through Solid-i18next. The settings UI enumerates `supportedProductLocales`, displays each locale through `settings.localeNames.<locale>`, and calls `setProductLocale` on selection.

The public function accepts the compile-time `ProductLocale` type, but it has no runtime validation. JavaScript callers or untyped boundaries can pass an arbitrary string; the function will persist it, update `<html lang>`, and ask i18next to switch. Validate external input before calling it. Likewise, local-storage reads and writes are not wrapped in `try/catch`; an environment whose storage API throws can fail module initialization or switching rather than silently falling back.

## Traditional Chinese generation

[`scripts/generate-zh-tw.mjs`](../../packages/i18n/scripts/generate-zh-tw.mjs) imports `zhCN` from `../dist/locales/zh-CN.js`, creates an OpenCC converter with `from: "cn"` and `to: "twp"`, and recursively maps strings through the converter. Arrays and nested objects are rebuilt recursively; non-string primitive values are returned unchanged. It writes a complete TypeScript module to `src/locales/zh-TW.generated.ts` with a generated-file header and an `as const` `zhTW` export.

This is phrase-level conversion of product copy, not independent translation ownership. Review user-facing Taiwan output in the generated artifact and update the Simplified Chinese source or the generation strategy when conversion is incorrect. Never hand-edit the generated output: the next generation overwrites it.

## Build, test, and contributor workflow

The package scripts are defined in [`package.json`](../../packages/i18n/package.json):

| Command | Effect |
| --- | --- |
| `npm run build --workspace @bear-harness/i18n` | Compile source to `dist`, generate Taiwan source from the newly compiled `dist` Simplified Chinese module, then compile again so generated source and declarations are emitted. |
| `npm run generate:locales --workspace @bear-harness/i18n` | Run the generator directly. It does not compile first. |
| `npm run typecheck --workspace @bear-harness/i18n` | Run `tsc -p tsconfig.json --noEmit` against `src/**/*.ts`. |
| `npm run test:unit --workspace @bear-harness/i18n` | Run the package's Vitest suite, including `catalogs.spec.ts`. |

Recommended copy-change sequence:

1. Add or change the product key in `src/locales/zh-CN.ts`.
2. Add the corresponding key and equivalent placeholders to `src/locales/en.ts`.
3. Run the package build so `dist/locales/zh-CN.js` is refreshed before OpenCC generation and the second compile emits the generated Taiwan module.
4. Review the generated `src/locales/zh-TW.generated.ts` for wording and placeholders; do not edit it manually.
5. Run the package typecheck and unit test commands. The unit test is the structural and language-content gate.

For a copy-only change, the focused commands above are sufficient verification. A new locale is a code change rather than a copy-only change: update the locale registry and resources, add its names to each catalog, update the supported-locale test expectation, and ensure the package exports/build include it.

## Error and security boundaries

The i18n module does not fetch translations, read package files, or execute package behavior. Catalogs are local TypeScript constants. The only persistence side effect is the locale string in `localStorage`; the only document side effect is `<html lang>`. Product UI and package content remain separate inputs at the application boundary.

The module intentionally does not await or handle the promises returned by `i18n.init` and `i18n.changeLanguage` (`void` is used for both). `initAsync: false` makes initialization synchronous in normal operation, but startup or language-switch failures are not surfaced by this module. Callers needing an explicit failure state must wrap their own operation or add handling at the application boundary.

## Extension points

- **New product copy:** extend the canonical `zh-CN` tree, mirror it in `en`, and regenerate Taiwan output.
- **New product surface:** add a top-level namespace to all catalogs and use dotted keys; the `ns: Object.keys(zhCN)` initialization will include it automatically.
- **New locale:** add a locale module, register/export it in `src/locales/index.ts`, add its locale name in the catalogs, and update tests and supported-locale typing.
- **Different Taiwan policy:** change the generator's OpenCC conversion or replace it with an explicitly maintained catalog only as a deliberate ownership decision; otherwise generated output will be overwritten.
- **Consumer integration:** use the shared `i18n` instance with `I18nextProvider`, `useTranslation`, and `useLanguage`; do not create a second product i18next instance in a consuming app.

## Known issues / findings

1. **Direct locale generation has a stale-dist hazard.** `generate-zh-tw.mjs` imports `../dist/locales/zh-CN.js`, not the TypeScript source. Running `generate:locales` after editing `src/locales/zh-CN.ts` without first compiling can fail when `dist` is absent or regenerate Taiwan copy from an older catalog when `dist` exists but is stale. The package `build` script avoids this by compiling before generation, but the standalone script does not enforce freshness.
2. **Two-stage build is required by the current generator.** The first `tsc` in `build` is not redundant: it produces the JavaScript module that the generator imports. The second `tsc` is what emits the newly generated source into `dist`. Skipping either stage leaves a broken or stale package artifact.
3. **Published/package exports point at `dist`.** `@bear-harness/i18n` and its `/locales` subpath resolve compiled files, while source edits live under `src`. Consumers can therefore observe old copy until the package is rebuilt. This is especially easy to miss when tests import the public workspace package rather than a source-relative module.
4. **English parity is runtime-tested, not statically declared.** `en` is an `as const` object but is not typed as `typeof zhCN`; a missing or extra English key is found by the catalog shape test, not by TypeScript alone. Keep the unit test in the localization change loop.
5. **Runtime locale input is not guarded by the public function.** `setProductLocale` relies on its TypeScript parameter and does not repeat `isProductLocale` at runtime. Untyped callers can persist and apply unsupported values.
6. **Interpolation delimiters are inconsistent in the catalog.** `canonStudio.sourceLanguage` uses `{{language}}` despite the module's explicit `{...}` delimiter configuration. Treat this as a copy/runtime contract to investigate before reusing the double-brace form.
7. **Storage and language-change failures are unobserved.** Local-storage operations and i18next initialization/language switching are performed without error handling. Environments with throwing storage APIs or rejected i18next operations receive no module-level diagnostic or recovery path.
