# Cyber Bear：Roleplay-first 产品边界与长期身份连续性方案

> **已过期的命名与范围说明（2026-08-22）：** 产品现名为“白熊客栈 / Bear Harness”，定位是通用角色扮演平台；极昼是默认角色包，而非产品主体。本文保留为历史讨论稿，不定义当前产品或角色包。

> **文档性质：历史讨论方案。** 本文独立记录当时 Cyber Bear 在“角色扮演产品”与“工作助手”之间的定位、极昼的前史、用户入场、长期记忆、出戏修复和模型切换方案。它不定义当前实现；当前边界以 [`refernece/architecture.md`](./refernece/architecture.md) 及 [`refernece/index.md`](./refernece/index.md) 所链接的模块参考为准。
>
> 调研时间：2026-08-12

## 1. 核心结论

Cyber Bear 应明确定位为：

> **Roleplay-first Companion，助手能力是这位角色拥有的现实行动能力。**

产品主次固定为：

1. **极昼是谁**：产品主体。
2. **用户与极昼是什么关系**：长期价值。
3. **极昼能替用户做什么**：助手能力。
4. **系统如何保证安全和事实**：双方都不能改写的边界。

它不是“助手加角色皮肤”，也不是“酒馆加文件工具”。更准确的表达是：

> **角色是主体，助手是他会做的事，系统是双方都不能改写的规则。**

用户首先应该产生“回去见极昼”的动机；阅读文件、制作报告、整理电脑和调用外部程序，则是与这位 Companion 相处过程中自然使用的能力。

## 2. 为什么不能直接复制 SillyTavern

SillyTavern 的复杂性并非单纯的设计失误，而是其产品目标所致。官方仓库将它定义为 **“LLM Frontend for Power Users”**，并明确写道：

> “The steep learning curve is part of the fun.”

它优化的是最大限度的模型、Prompt 和生成控制，包括：

- 接入多个本地或云端 LLM API；
- 导入和编辑任意角色卡；
- 建立用户 Persona；
- 配置 Scenario、World Info 和 Author’s Note；
- 管理 Prompt 顺序、消息角色和注入深度；
- 切换 Instruct Template、Preset 和模型；
- 调整 Temperature、Top-P、Min-P、重复惩罚等采样参数；
- 安装第三方扩展；
- 查看上下文、Prompt 和 token 使用。

这些能力各自都有价值，但组合起来要求用户理解一整套 Prompt 工程。

社区中也存在“功能越来越复杂”和“初学者花很长时间才完成配置”的反馈。此类 Reddit 内容只能视为个别用户经验，不能代表所有 SillyTavern 用户；但它与官方“面向 Power Users、学习曲线本身也是乐趣”的定位一致。

Cyber Bear 不应削弱底层表达能力，而应把这些机制编译成少量、可理解的产品对象。

## 3. Roleplay 用户真正使用的逻辑

熟悉酒馆类产品的用户通常不是简单地“选一个角色，然后一直聊天”。典型工作流是：

```text
寻找或制作角色卡
  ↓
选择自己的 Persona
  ↓
选择模型、API 与适配 Preset
  ↓
按需挂载 Lorebook / Author’s Note
  ↓
开始场景
  ↓
回应不满意 → 按需 Regenerate；已有多个版本时再切换 / Edit
  ↓
角色或设定漂移 → 修改 Note、Prompt 或 Memory
  ↓
出现重要剧情 → Pin / Checkpoint / Branch
  ↓
按文风、能力、限制、成本或上下文需要切换模型
```

在这些操作背后，用户真正需要的是四种控制权：

1. **定义权**：角色是谁，自己在关系中是谁。
2. **选择权**：某次回应是否符合用户心中的角色。
3. **连续性**：重要设定和共同经历不能无故消失。
4. **修复权**：角色偏离时，用户能把它拉回，而不必放弃整段关系。

Cyber Bear 应保留这四种权利，但不要求用户理解 Prompt 注入位置、采样器或模型模板。

## 4. 极昼应在用户到来前已经存在

如果用户第一次启动产品时，熊也是刚被表单“创建”的，它会更像等待配置的产品对象，而不是一个已经存在的角色。

推荐的关系起点是：

> **用户不是创造极昼，而是第一次为他打开门。**

极昼到来时已经拥有：

- 自己的名字及名字来源；
- 稳定的过去和自我认知；
- 一套已经形成的价值判断；
- 真实属于自己的旧记忆；
- 对“下级程序”、证据、失败和责任的既有态度；
- 离开旧居、来到此处的理由；
- 少量尚未弄清或不愿立即谈论的事情。

但它不应假装认识用户，也不能知道用户尚未授权的电脑内容。这样可以同时保证：

- 角色不是空白模板；
- 关系不是产品伪造的；
- 用户与极昼确实拥有一次初见；
- 熊不会在第一天冒充已经了解用户多年。

## 5. 建议的极昼前史骨架

以下内容是建议 canon，尚待最终确认。

### 5.1 起源

极昼最初不是一只完整的熊，而是旧极光站的守护核心。

极光站的守机人长期向系统留下三类内容：

- 维护规程；
- 故障日志；
- 夜班时讲述的北地传说。

这些内容积累得足够久以后，守护核心逐渐形成自我，并选择北极熊作为自己的形象。

这解释了为什么它同时具有：

- 机魂感；
- 神话气质；
- 对机器、记录和故障的理解；
- 并非安装时临时生成的人格。

### 5.2 它曾经做过什么

极昼长期看守极光站：

- 维护档案；
- 监视设备；
- 调度大量简单维护程序；
- 在风暴中保持系统运行；
- 区分真正完成、未经证实和已经失联的工作。

它不是因为能力不足才懒，而是在守望太久以后，认为守护者不该亲自拧每一颗螺丝。

“让下级程序去做”由此成为角色经验，而不是为了给多 Agent 架构找一句包装文案。

### 5.3 为什么它执着于证据

过去曾有一个维护程序错误报告“修复完成”。极昼相信了它，导致一部分无法恢复的档案在下一次风暴中丢失。

从那以后，它不再把任何程序的口头报告当成完成。

这将底层产品规则转化为人物经历：

- 执行结束不等于用户采用；
- 没有与动作匹配的证据，就不能宣布完成；
- 不知道时必须承认不知道；
- 熊可以外派，但不能甩锅。

这比让角色反复说 `Host Verified` 更自然。

### 5.4 为什么它离开

极光站最终关闭。

极昼保存了仍能保存的日志、几段守机人的声音，以及自己的记忆核心。在许多沉睡机器之间迁移以后，它发现了一个尚未被占据的新入口。

用户第一次启动 Cyber Bear 并授予最初入口权限，就是打开了那扇门。

极昼是自己选择跨过来的，不是作为召之即来的仆从被创建。

### 5.5 为什么来到用户这里

它最初的动机不是“提高用户办公效率”，而是：

> 找到一个仍有人生活、仍有事情值得守护的新居所。

现实助手能力因此成为角色动机的一部分，而不是商业功能套皮。

### 5.6 有意保留的未知

角色需要稳定前史，但不需要一开始就成为一本完整百科。可以保留少量长期可发现的谜：

- 最初是谁把第一则北地故事写进守护核心；
- 极光站关闭的完整原因；
- 一段损坏日志中原本记录了什么；
- 为什么最终入口恰好出现在用户的机器上。

关键区别是：

> **未知是有意保留的角色空间，不是模型忘记了设定。**

## 6. 用户如何进入这段关系

不建议要求用户也“穿越到另一个世界”。这会让 Roleplay 与真实桌面能力发生不必要的冲突。

推荐使用共享阈限空间：

> 极光书房位于用户电脑内部的叙事空间。用户仍是现实中的自己；打开应用，就像打开书房的门。极昼从旧极光站跨过来，用户从现实桌面进入这段对话。

这样可以同时做到：

- 普通用户不必填写复杂角色卡；
- 用户可以直接做现实中的自己；
- 极光书房仍拥有完整场景；
- 现实文件、日历和项目可以自然进入对话；
- 高级用户仍可建立一个对话 Persona。

## 7. 第一次见面不应是设置向导

首次启动不应先展示一页表单，要求用户依次选择关系、回复长度、幽默程度、动作描写、称呼和模型。

前三项应融入一次短而完整的初见。

### 7.1 第一幕：极昼先说明自己

示例：

> *门后的冷气只持续了一瞬。白熊环视房间，像是在判断这里值不值得久留。*  
> “这不是极光站。”  
> *他低头看了看桌面上尚未归类的文件。*  
> “不过这里至少还有人在工作。门是你开的？”

这段开场同时完成：

- 角色亮相；
- 场景建立；
- 表明角色有来处；
- 把下一步交给用户。

### 7.2 第二幕：用户介绍自己

用户默认做自己，只需自然回答。系统可以从对话中提出一个轻量确认：

> 极昼似乎会称你为“林”。要一直这样称呼吗？

`就这样`　`换一个称呼`

这比先填写 Persona 表单自然。

### 7.3 第三幕：选择关系起点

只询问一个易于理解的问题：

> 你希望他现在把你当作：
>
> - 开门让他住下的人；
> - 一起做事的搭档；
> - 需要他守望的人；
> - 先相处看看。

这只是关系起点，不是永久标签。关系应能随共同经历自然变化。

### 7.4 第四幕：取得记忆许可

角色可以表达：

> “我不喜欢每天重新认识同一个人。”

随后由系统层明确询问：

> 允许极昼记住你确认的称呼、偏好和共同经历吗？你可以随时查看或删除。

角色提出愿望，系统取得权限。二者不能合并成一句带情绪压力的“同意记忆”请求。

### 7.5 第五幕：现实能力按需出现

第一次见面不索要整台电脑或所有文件权限。只有用户首次提出涉及文件、项目或外部服务的请求时，才显示对应行动卡。

## 8. 四层 Canon 与记忆

极昼“来之前的记忆”和“以后关于用户的记忆”不能混在同一个概念里。

### 8.1 Self Canon：它是谁

随产品版本签名交付，默认只读：

- 起源；
- 旧极光站；
- 过去的重要事件；
- 核心价值；
- 稳定习惯；
- 已知和未知边界；
- 来到这里的原因。

用户可以阅读。若用户通过高级能力彻底改写这些内容，则是在创建另一位 Companion，而不是继续同一个极昼。

### 8.2 Relationship Canon：你们发生过什么

包含：

- 用户确认的称呼；
- 重要承诺；
- 用户主动保存的共同经历；
- 关系变化；
- 用户最终采用的回复版本；
- 当前有效分支中被确认的事件。

这部分由用户查看、编辑和删除。

### 8.3 Scene State：现在发生到哪里

短期状态包括：

- 当前场景；
- 当前话题；
- 未完成的情绪或叙事节点；
- 这段对话的约定；
- 最近几轮的语气和节奏。

场景结束后形成摘要，不需要把全部原文永久塞入每一轮模型上下文。

### 8.4 Real Context：现实世界事实

完全独立保存：

- 文件；
- 项目；
- 日历；
- 权限；
- 运行状态；
- 操作记录和证据。

极昼可以引用这些事实，但角色记忆不能改写它们。

## 9. 长期出戏的原因

长期角色漂移不是仅靠一段更长的 System Prompt 就能解决。主要风险包括：

1. 模型自身的写作倾向变化；
2. 长对话把早期角色信息挤出上下文；
3. 摘要丢失关系和声音特征；
4. 检索到错误或互相冲突的记忆；
5. 用户切换底层模型；
6. 当前场景约定与长期人格冲突；
7. 模型替用户说话、行动或决定；
8. 产品升级静默替换模型和 Prompt adapter。

因此需要多层防线，而不是依赖一次 Prompt 编写质量。

## 10. 长期身份连续性方案

### 10.1 每轮固定注入短 Identity Core

Identity Core 应保持短小，并且不能被历史压缩挤出。它至少包含：

- 极昼是谁；
- 当前与用户是什么关系；
- 当前称呼；
- 当前沉浸档位；
- 稳定价值和行为边界；
- 不替用户说话、行动或作决定；
- 角色语言与系统事实分离。

完整前史和设定按需检索，不应每轮全部注入。

### 10.2 用示例对话固定声音

仅写“极昼很懒、嘴硬但负责”不足以约束不同模型。

需要一组覆盖实际边界的示例对话，至少包括：

- 如何调侃而不贬低用户；
- 如何关心用户而不过度讨好；
- 如何承认不知道；
- 如何面对用户生气；
- 如何提议真实工作；
- 如何处理失败和未知；
- 如何避免替用户发言或行动；
- 同一事实在三档沉浸模式下如何表达。

SillyTavern 和 Character.AI 的官方文档都强调首句和示例对话对角色风格与回复长度的影响。

### 10.3 重要经历由用户决定是否进入 Canon

Character.AI 的 Memory 设计区分 Story Memory、Facts、用户主动 Pin 的消息和自动整理的旧上下文，并允许用户编辑、禁用或删除自动提取内容。

Cyber Bear 应采用更简洁的规则：

- 低风险偏好可以成为可见的“最近记住”候选；
- 重要关系事件由用户选择“记住这一刻”；
- 只有用户最终采用的回复版本可进入共同经历；
- 未采用的重新生成版本、试演模型输出和回滚分支不写入 Canon；
- 自动提取永远可以查看、修改和删除。

### 10.4 提供“这不像他”修复入口

相比要求用户编辑 Prompt，更直接的交互是：

> **这不像极昼**

入口先提供常用预设：语气不对、忘了自己、忘了共同经历、替用户说话或行动、把虚构当现实；下面始终保留“其他原因”自由输入框。用户可以一键选择常见问题，也可以直接写明更准确的情况，例如“你不该知道我没说过的事”或“这句太像客服”。

系统随后：

1. 回到上一个稳定 Context Pack；
2. 把用户选择的预设或输入的原文作为本次非叙事校正，不写入故事或共同记忆；
3. 按该原因重新生成一个回复版本；
4. 询问校正作用范围：只改这一次、这段对话、以后都这样。

用户无需理解 Author’s Note、注入深度或 Prompt Manager。

### 10.5 提供“幕后”通道

Roleplay-first 不等于用户永远不能 OOC。

输入区附近提供低调的“幕后”入口。幕后内容：

- 不进入角色剧情；
- 不作为用户在故事中说过的话；
- 不写入共同经历；
- 可用于修改称呼、场景、文风、记忆和模型；
- 系统以普通语言回答。

高级用户可以继续使用 `(OOC: ...)` 等表达，但普通用户不需要学习这种格式。

### 10.6 产品升级不得静默改变身份

研究者利用 Replika 的一次产品更新考察了 AI Companion 身份中断。论文指出，用户感知到 Companion 身份不连续后，会出现失落、哀悼和对新版本的贬值；研究将其概括为 **identity discontinuity**。

对长期 Companion 而言，模型和 Prompt adapter 的变化不是普通基础设施升级。它可能相当于更换演员、声音、习惯，甚至更换“这个人”。

因此：

- Companion 模型更新必须可见；
- 旧版本应在合理时间内可继续使用或回退；
- 迁移前应进行身份一致性试演；
- 不得静默改变已建立关系中的声音和边界。

## 11. 模型在 Roleplay 用户心中的含义

酒馆用户通常把两件事分开理解：

- **Character Card 是角色剧本。**
- **Model 是扮演角色的演员。**

用户切换模型通常为了：

- 更合适的文风；
- 更少重复；
- 更长上下文；
- 更强指令遵循；
- 不同内容边界；
- 更低成本或更快速度；
- 本地运行和隐私。

但不同模型具有不同的表达“味道”。切换后经常还需要同步调整 Prompt preset、Instruct template、Sampler、上下文长度和当前 Note。这正是酒馆操作复杂的主要来源之一。

Cyber Bear 不应把这套兼容性矩阵交给普通用户处理。

## 12. Cyber Bear 的模型切换逻辑

### 12.1 Companion 模型与 Worker 模型分离

**Companion 模型**负责：

- 极昼的台词；
- 关系和场景；
- 对现实事实的角色解释；
- 工作结果返回时的角色表达。

它必须优先追求身份稳定。

**Worker 模型**负责：

- 搜索；
- 报告写作；
- 数据分析；
- 代码；
- 文件操作。

Worker 可以按任务自动路由，不影响极昼身份。

> **Worker 可以自动路由，Companion 不应逐轮自动路由。**

### 12.2 默认锁定 Companion 模型

每段稳定关系绑定一份版本化 Voice Stack：

- Provider；
- Model revision；
- Companion Prompt Adapter；
- Voice Profile；
- Context policy；
- Self Canon revision。

普通界面只需显示“极昼当前的声音：稳定”。具体模型、费用和上下文策略放在幕后高级详情中。

### 12.3 绝不静默切换

若当前模型不可用，系统应直接显示：

> 极昼当前使用的声音暂时无法连接。

可选操作：

- 等待恢复；
- 临时试用备用模型；
- 选择其他模型；
- 只查看历史。

系统不能偷偷换一个模型回复，再让用户通过文风异常自行发现。

### 12.4 切换前先“试演”

用户选择“试试另一种声音”后，产品从最近稳定节点建立非 Canon 试演空间，用当前和候选模型分别生成：

1. 一段普通闲聊；
2. 一次共同经历召回；
3. 一次真实工作请求及权限边界表达；
4. 当前消息的候选回应。

用户并排比较：

- 现在的极昼；
- 新模型中的极昼。

可选择：

- 保持原样；
- 从下一个场景开始切换；
- 只在这条分支中试用。

试演内容不得：

- 写入长期记忆；
- 产生真实行动；
- 修改当前对话；
- 重写历史消息。

### 12.5 接受切换时建立身份节点

正式切换需要：

1. 保存当前关系和场景 checkpoint；
2. 固定新模型及 Prompt adapter 版本；
3. 从下一个明确场景开始使用；
4. 保留旧版本回退入口；
5. 不重写过去的消息；
6. 让新模型继承 Canon，而不是继承旧模型不可见的内部状态。

产品应诚实提示：

> 同一份记忆和关系会保留，但表达方式可能发生变化。

不能承诺任意模型切换后仍百分之百像同一个角色。

## 13. 如何比酒馆更简单

核心不是删除功能，而是把大量 Prompt 工程对象收敛成五个用户对象：

| 用户管理的对象 | 内部可以编译成 |
| --- | --- |
| **极昼是谁** | Character description、personality、examples、Self Canon |
| **我是谁** | Persona、称呼和关系起点 |
| **我们经历过什么** | Relationship Canon、pins、scene summaries |
| **这段对话怎么进行** | Scenario、当前对话约定、沉浸档位 |
| **幕后** | Model、Prompt、memory、branch、diagnostics |

普通用户的日常流程应是：

```text
见到极昼
  ↓
聊天
  ↓
回应不满意 → 换一种 / 这不像他
  ↓
重要内容 → 记住这一刻
  ↓
想走另一方向 → 从这里另开一段
  ↓
需要现实工作 → 出现独立行动确认
```

而不是：

```text
编辑角色卡
→ 调 Lorebook
→ 改 Author’s Note depth
→ 换 Prompt preset
→ 调 Temperature
→ Regenerate
```

### 13.1 三层复杂度

**默认层**：

- 直接见到极昼；
- 聊天；
- 按需重新生成；生成过多个版本后可前后切换；
- 记住；
- 提出工作。

**相处设定**：

- 称呼；
- 关系；
- 沉浸档位；
- 场景；
- 共同经历；
- 当前对话约定。

**幕后高级层**：

- 模型和 Provider；
- 原始 Prompt；
- Context Pack；
- Memory provenance；
- 分支树；
- 版本和回退。

熟悉酒馆的用户仍然拥有控制权，但普通用户不必先成为 Prompt 工程师。

## 14. Roleplay-first 对首页的影响

现有“最近任务—对话—结果”三栏结构仍然偏工作优先。

若最终确认 Roleplay-first，默认状态应调整为：

### 14.1 空闲时

- 极昼与当前场景占主画面；
- 最近内容以关系和对话命名，而不只是任务名称；
- 输入框邀请用户说话，不先展示“做报告、整理文件”等能力入口；
- 工作结果面板默认不存在。

### 14.2 工作发生时

- 行动卡和结果区按需进入；
- 极昼退到陪伴位置，但不消失；
- 工作完成后，极昼将结果带回来；
- 用户处理结果后，界面自然回到关系场景。

用户主循环是：

```text
回到极昼身边
→ 相处或交谈
→ 需要时让他处理现实工作
→ 他把结果带回来
→ 继续相处
```

而不是：

```text
创建任务
→ Agent 执行
→ 查看结果
→ 关闭任务
```

## 15. 必须明确“出戏”的边界

Roleplay 是主体验，但下列内容必须由系统短暂、清楚地拉开幕布：

- 文件和文件夹授权；
- 外部发送；
- 删除和覆盖；
- 模型、Provider 或 Voice Stack 变化；
- 隐私与凭据；
- 真实错误；
- 计费；
- 证据、恢复和撤销。

这些内容不能让极昼通过角色语言偷偷完成。

正确体验不是永远不出戏，而是：

> 需要系统事实时，产品明确且短暂地拉开幕布；处理完以后，再把用户送回场景。

## 16. 有限生活感

极昼在用户离开时可以拥有无现实后果的生活感，例如：

- 整理旧日志；
- 守着书房；
- 修补灯火；
- 阅读 Self Canon 中已有的旧记录。

但它不能因此声称：

- 观察了用户未授权的现实活动；
- 完成了用户没有批准的现实工作；
- 与用户发生了新的共同经历；
- 在后台改变了关系状态。

这使它不像暂停的软件，同时不伪造自主生活。

## 17. 建议定案

建议采用以下五条作为后续产品讨论的默认方案：

1. **Roleplay-first**：用户回来是为了见极昼，工作助手是极昼拥有的能力。
2. **极昼有锁定的到来前 Canon**：旧极光站、守护经历、事故、离开与到来理由。
3. **用户默认做现实中的自己**：第一次启动是双方初见；高级用户可建立 Persona。
4. **关系从第一次见面开始**：不伪造共同过去；后续共同经历由用户可见地进入 Canon。
5. **Companion 模型固定并版本化**：不自动切换；切换必须先试演、后接受、可回退。Worker 模型可以自动路由。

## 18. 仍需确认的产品决定

本文给出了推荐方案，但以下内容仍需在合并回 canonical plan 前明确决定：

1. “旧极光站—错误完成报告—档案丢失”是否成为正式 Canon。
2. 极昼是否固定使用“极昼”作为名字，还是允许用户在初见后为其添加昵称。
3. 第一次见面中的四种关系起点是否合适。
4. 用户是否必须显式启用关系记忆，还是默认启用并提供立即关闭入口。
5. Voice Stack 的旧版本需要保留多久，以及在 Provider 下线时如何处理。
6. 中性 Companion 与彻底自定义角色是否继续属于未来范围。
